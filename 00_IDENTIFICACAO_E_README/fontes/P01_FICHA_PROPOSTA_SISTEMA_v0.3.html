3. Opção 1: Sistema Saborino (escolhida)

Nome do sistemaSistema Saborino: gestão de uma pequena produção de alimentos (release a63a24f)
Origem do sistemaDesenvolvido anteriormente por um integrante, Leonardo Valentim (seção 5.2). Os testes usam somente uma cópia local, com banco próprio e dados fictícios.
Link do repositóriohttps://github.com/LeonardoVDN/P2_TQS_2026_CC_GRUPO13_SABORINO (público). O código fica em 01_SISTEMA_ALVO/saborino.
Licença/autorizaçãoO código é de autoria do integrante, que autoriza o uso acadêmico e as alterações de TDD. A cópia publicada foi anonimizada, e os desvios da release estão em 01_SISTEMA_ALVO/DESVIOS_DA_RELEASE.md. Os dados são somente fictícios.
Tecnologias principaisPython 3.12, Django 5.2, Django REST Framework, PostgreSQL 15, Vue 3 com Vite, Pinia e Axios, autenticação por sessão (cookie e CSRF), Celery e Redis (só para e-mail)
Como executarDocker (forma A): docker compose -p p2tqs-saborino sobe banco, API (:8000) e frontend (:5173), depois roda migrate e o seed fictício. Linux sem Docker (forma B): script ambiente_p2/p2_linux.sh. Os passos completos estão no README da pasta 00.
Fluxos selecionados (preliminar)
  • F1 Autenticação: login e logout por sessão
  • F2 Cadastro de clientes: nome, canal, contato e forma de pagamento
  • F3 Cadastro de produtos: preço, custo, categoria e unidade
  • F4 Registro de venda: itens, cálculo do total e geração do recebível
  • F5 Recebimento: pagamento parcial ou total que abate recebíveis
  • F6 Compras e produção: lançamento de insumos com rateio por produto
  • F7 Relatórios: painel e fechamento mensal
Integrações existentesFrontend Vue ↔ API REST (Axios, JSON, sessão e CSRF); API ↔ PostgreSQL (ORM do Django); integração entre módulos (Venda → Recebível → Pagamento/Alocação → Relatórios); API ↔ Celery/Redis ↔ provedor de e-mail (fora do escopo)
Justificativa da escolhaAtende a todos os itens da seção 5.3, com 7 fluxos e 5 formulários. O grupo tem acesso total ao código e conhece o domínio. As regras de cálculo (totais, saldos, status) servem bem para valor limite e partição de equivalência. A API REST permite usar o Postman, e a interface web permite usar o Selenium. Já existe uma suíte de 69 testes para comparar com os testes do grupo.
Riscos de viabilidade
  • Risco de afetar dados reais: mitigado com uma cópia local isolada, banco próprio e dados fictícios.
  • O e-mail depende de Celery, Redis e um provedor externo: esses fluxos ficam fora do escopo.
  • O sistema é maior que o necessário: o escopo fica restrito aos fluxos F1 a F7.
  • A linguagem não é Java: pedimos autorização para usar pytest no lugar do JUnit (seção 8.3).

4. Classificação preliminar dos níveis de teste

Nível / tipoFinalidade no SaborinoFerramenta prevista
UnitárioRegras isoladas: arredondamento monetário, subtotal do item, total da venda, status do recebível (Aberto, Parcial, Pago, Vencido) e competência derivada da datapytest e pytest-django
Integração / APICliente ↔ API ↔ banco: autenticação, cadastro de clientes e produtos, venda gerando recebível, pagamento abatendo saldo, respostas 2xx, 4xx e 401Postman e Newman
Sistema / interfaceFluxos ponta a ponta pela interface: login, cadastro de cliente, venda rápida e recebimentoSelenium WebDriver (Python)
Aceitação4 cenários do ponto de vista do usuário gestor, executados por uma pessoa externaRoteiro e registro (Aceito, Aceito com ressalvas ou Não aceito)
Não funcionaisDesempenho básico, compatibilidade (2 navegadores e resoluções), segurança básica e confiabilidade (reinício controlado)Scripts de medição, Selenium e navegador

Justificativa da estratégia: as regras de cálculo concentram o maior risco de erro silencioso (valores e saldos errados). Por isso, a base da pirâmide são os testes unitários dessas regras. A API é a fronteira principal entre os componentes e recebe os testes de integração. Os fluxos que o usuário mais repete (venda e recebimento) recebem os testes de sistema e de aceitação.

5. Opção 2: GreenOps Profiler (descartada)

Nome do sistemaGreenOps Profiler: protótipo que compara o consumo de energia entre versões de funções de backend
Origem do sistemaSistema acadêmico em desenvolvimento pelo grupo (TCC dos mesmos integrantes)
Link do repositórioNão publicado
Licença/autorizaçãoCódigo de autoria do grupo
Tecnologias principaisPython 3.11+, numpy, scipy e pytest. Há um backend Django de apoio, usado só como alvo das medições.
Como executarLinha de comando (cd sandbox; ./run.sh). Não tem interface web para o usuário final.
Fluxos selecionados (preliminar)Comparação de variantes pela linha de comando, autoteste A/A e geração de relatório em texto
Integrações existentesEntre módulos internos (runner, stats, report) e com a fonte de energia (RAPL ou simulada)
Justificativa da escolhaO grupo domina o código, e ele tem muita lógica testável por unidade.
Riscos de viabilidade
  • Não atende à seção 5.3: faltam interface web e ao menos 2 formulários, o que inviabiliza Selenium e Postman.
  • A medição por RAPL não existe no hardware disponível (Apple Silicon).
  • Mistura a avaliação da P2 com o TCC.
